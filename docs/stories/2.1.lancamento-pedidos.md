## Story
**As a** Tiago ou Diego (vendedor),
**I want** lancar pedidos selecionando o cliente e adicionando produtos com quantidades,
**so that** o pedido fique registrado e pronto para confirmacao, com precos corretos por cliente carregados automaticamente.

## Scope

### IN
- Tabelas `orders` e `order_items` com RLS multi-tenant
- Supabase function `create_order` (PL/pgSQL) com snapshot de precos e nomes
- Supabase function `update_order` para edicao atomica
- Zustand cart store com calculos real-time (subtotal, custo, lucro)
- Componentes: busca cliente (autocomplete), busca produto, lista de itens, resumo financeiro
- Pagina Novo Pedido e Editar Pedido
- Hook `use-orders` para CRUD
- Integracao com `client_prices` (preco customizado por cliente)

### OUT
- Lista de pedidos com filtros e status (Story 2.2)
- Fluxo de confirmacao/carregamento (Story 2.3)
- Impressao termica (Story 2.4)
- Devolucao parcial (Story 2.5)
- Desconto manual no pedido (futuro)
- Envio de pedido por WhatsApp

## Dependencies
- **Story 1.3** (Multi-Conta) — COMPLETED. accounts, account_users, RLS functions
- **Story 1.4** (Produtos) — COMPLETED. products, product_variants
- **Story 1.5** (Clientes) — COMPLETED. clients, client_prices, price-resolver

## Complexity
- **Estimate:** XL (Extra Large)
- **Points:** 13
- **Rationale:** 2 tabelas + 2 functions PL/pgSQL + RLS + Zustand store + 4 componentes + 2 paginas + hook. Story mais complexa ate agora: envolve logica server-side (functions), state management client-side (cart), e integracao de 3 entidades (clients, products, orders).

## Risks
- **R1:** Function PL/pgSQL `create_order` e complexa (loop + COALESCE + snapshots). **Mitigacao:** Testar com dados de seed, validar totais no banco.
- **R2:** Cart store pode ficar dessincronizado com precos do banco se outro usuario alterar precos durante a criacao. **Mitigacao:** Aceitavel — precos sao snapshottados no momento do save via function server-side.
- **R3:** Edicao de pedido em status avancado (Confirmado, Carregado) pode causar inconsistencias. **Mitigacao:** Recalcular totais via `update_order` function.
- **R4:** Autocomplete de cliente/produto pode ter performance ruim com muitos registros. **Mitigacao:** Debounce 300ms + LIMIT 10 na query.

## Acceptance Criteria
1. Tela "Novo Pedido": selecionar cliente via busca com autocomplete; ao selecionar, precos customizados sao carregados automaticamente
2. Adicionar produtos com quantidade via busca rapida por nome; quantidade com botoes +/- touch-friendly
3. Exibir total do pedido (faturamento e lucro estimado) em tempo real conforme itens sao adicionados/alterados
4. Salvar pedido com status "Lancado" vinculado a conta ativa e ao usuario que criou
5. Edicao de pedido em qualquer status (Lancado, Confirmado, Carregado) sem precisar excluir e relancar
6. Pedido vinculado a conta ativa e ao usuario que criou (created_by)
7. Forma de pagamento pre-selecionada com o padrao do cliente, editavel
8. Campo de observacoes (notas) opcional no pedido

## Dev Notes

### Database Tables Envolvidas

**`orders`** (principal):
```sql
CREATE TABLE public.orders (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  account_id UUID NOT NULL REFERENCES public.accounts(id) ON DELETE CASCADE,
  client_id UUID NOT NULL REFERENCES public.clients(id),
  created_by UUID NOT NULL REFERENCES public.users(id),
  order_number SERIAL,
  status TEXT NOT NULL DEFAULT 'lancado'
    CHECK (status IN ('lancado', 'confirmado', 'carregado', 'entregue', 'cancelado')),
  payment_method TEXT CHECK (payment_method IN ('dinheiro', 'pix', 'boleto', 'vale', 'cartao', 'misto')),
  subtotal NUMERIC(12,2) NOT NULL DEFAULT 0,
  total_cost NUMERIC(12,2) NOT NULL DEFAULT 0,
  profit NUMERIC(12,2) NOT NULL DEFAULT 0,
  discount NUMERIC(10,2) NOT NULL DEFAULT 0,
  total NUMERIC(12,2) NOT NULL DEFAULT 0,
  notes TEXT,
  delivery_date DATE,
  delivered_at TIMESTAMPTZ,
  confirmed_at TIMESTAMPTZ,
  loaded_at TIMESTAMPTZ,
  cancelled_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**`order_items`**:
```sql
CREATE TABLE public.order_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id UUID NOT NULL REFERENCES public.orders(id) ON DELETE CASCADE,
  account_id UUID NOT NULL REFERENCES public.accounts(id) ON DELETE CASCADE,
  product_variant_id UUID NOT NULL REFERENCES public.product_variants(id),
  product_name TEXT NOT NULL,       -- snapshot at order time
  variant_name TEXT NOT NULL,       -- snapshot at order time
  quantity NUMERIC(10,3) NOT NULL,
  unit_price NUMERIC(10,2) NOT NULL, -- price at order time (custom or default)
  cost_price NUMERIC(10,2) NOT NULL, -- cost at order time
  total NUMERIC(12,2) NOT NULL,      -- quantity * unit_price
  total_cost NUMERIC(12,2) NOT NULL, -- quantity * cost_price
  is_returned BOOLEAN NOT NULL DEFAULT false,
  returned_quantity NUMERIC(10,3) DEFAULT 0,
  return_reason TEXT,
  returned_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**`client_prices`** (para preco customizado):
```sql
CREATE TABLE public.client_prices (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  account_id UUID NOT NULL REFERENCES public.accounts(id) ON DELETE CASCADE,
  client_id UUID NOT NULL REFERENCES public.clients(id) ON DELETE CASCADE,
  product_variant_id UUID NOT NULL REFERENCES public.product_variants(id) ON DELETE CASCADE,
  custom_price NUMERIC(10,2) NOT NULL,
  UNIQUE(client_id, product_variant_id)
);
```

### Supabase Function `create_order`

A function completa esta no architecture doc (secao 6.3). Pontos criticos:
- Usa `SECURITY DEFINER` para acessar `auth.uid()` como `created_by`
- Faz loop em `p_items` (JSONB array) para inserir `order_items`
- Para cada item, busca `client_prices.custom_price` e faz `COALESCE(custom_price, sell_price)`
- Snapshots `product_name` e `variant_name` no momento da criacao (imutavel)
- Retorna o UUID do pedido criado

### Logica de Preco por Cliente (Client-Side)

No cart store, ao selecionar cliente:
```typescript
// Buscar precos customizados
const { data: customPrices } = await supabase
  .from('client_prices')
  .select('product_variant_id, custom_price')
  .eq('client_id', clientId);

// Criar mapa de precos: variant_id -> price
const priceMap = new Map(customPrices.map(cp => [cp.product_variant_id, cp.custom_price]));

// Ao adicionar item ao carrinho, usar:
const unitPrice = priceMap.get(variantId) ?? variant.sell_price;
```

### RLS Policies (ja cobertas no Epic 1)

As orders seguem o padrao multi-tenant:
- SELECT: `account_id = ANY(get_user_account_ids())`
- INSERT: `account_id = ANY(get_user_account_ids()) AND role IN ('admin', 'vendedor')`
- UPDATE: mesma logica
- DELETE: admin only
