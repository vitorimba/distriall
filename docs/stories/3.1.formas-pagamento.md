## Story
**As a** Tiago (admin),
**I want** registrar a forma de pagamento de cada pedido (Dinheiro, Pix, Boleto, Vale, Cartao) incluindo pagamentos mistos,
**so that** o acerto semanal seja calculado automaticamente sem precisar anotar no bloco de notas.

## Scope

### IN
- Tabela `payments` com RLS multi-tenant + financial visibility
- Componente payment-selector (simples + modo misto)
- Integracao no fluxo de criacao/edicao de pedido
- Flag `is_third_party` automatica para boletos (Boa Mesa)
- Filtro por forma de pagamento na lista de pedidos
- Validacao soma payments = total do pedido (client + server)
- Tipos TypeScript + Zod no shared package

### OUT
- Confirmacao de pagamento (status pendente→confirmado) — Story 3.4
- Conciliacao bancaria automatica
- Integracao com gateway de pagamento
- Split de pagamento entre contas

## Dependencies
- **Story 2.1** (Lancamento de Pedidos) — COMPLETED. orders com campo payment_method
- **Story 1.5** (Clientes) — COMPLETED. clients.default_payment_method para pre-selecao

## Complexity
- **Estimate:** M (Medium)
- **Points:** 5
- **Rationale:** 1 tabela + RLS + 1 componente (payment-selector com modo simples/misto) + integracao nos forms existentes + filtro. Schema e logica bem definidos no Dev Notes.

## Risks
- **R1:** Pagamento misto com N linhas pode ficar confuso no mobile. **Mitigacao:** UI simples com "adicionar forma" e validacao soma em tempo real.
- **R2:** Soma dos pagamentos pode divergir do total por arredondamento. **Mitigacao:** Ultimo pagamento auto-completa o resto (total - soma dos anteriores).

## Acceptance Criteria
1. Campo `forma_pagamento` no pedido com opcoes: dinheiro, pix, boleto, vale, cartao, misto
2. Selecao da forma de pagamento na criacao/edicao do pedido, puxando o padrao do cadastro do cliente (`clients.default_payment_method`)
3. Boleto registrado como pagamento com flag visual indicando que "valor cai na conta da Boa Mesa" (campo `is_third_party = true` na tabela `payments`)
4. Pagamento misto permitido: ao selecionar "misto", exibir formulario para dividir o valor entre multiplas formas de pagamento (multiplos registros na tabela `payments`)
5. Filtro de pedidos por forma de pagamento na lista de pedidos
6. Soma dos pagamentos de um pedido deve ser igual ao total do pedido (validacao client-side e server-side)
7. RLS garante que pagamentos so sao visiveis para usuarios com acesso a conta

## Dev Notes

### Database Schema

Tabela `payments` (ja definida na architecture doc):

```sql
CREATE TABLE public.payments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  account_id UUID NOT NULL REFERENCES public.accounts(id) ON DELETE CASCADE,
  order_id UUID NOT NULL REFERENCES public.orders(id) ON DELETE CASCADE,
  method TEXT NOT NULL CHECK (method IN ('dinheiro', 'pix', 'boleto', 'vale', 'cartao')),
  amount NUMERIC(12,2) NOT NULL,
  status TEXT NOT NULL DEFAULT 'pendente'
    CHECK (status IN ('pendente', 'confirmado', 'cancelado')),
  is_third_party BOOLEAN NOT NULL DEFAULT false, -- true for boleto (Boa Mesa receives the money)
  notes TEXT,
  confirmed_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_payments_account ON public.payments(account_id);
CREATE INDEX idx_payments_order ON public.payments(order_id);
CREATE INDEX idx_payments_method ON public.payments(account_id, method);
CREATE INDEX idx_payments_status ON public.payments(status);
```

A tabela `orders` ja possui o campo `payment_method` com CHECK `('dinheiro', 'pix', 'boleto', 'vale', 'cartao', 'misto')`. Esse campo serve como "resumo" — o detalhamento fica na tabela `payments`.

### RLS Policies

```sql
-- SELECT: user can read payments from accounts they belong to
CREATE POLICY "Users can view own account payments"
  ON public.payments FOR SELECT
  USING (account_id = ANY(get_user_account_ids()));

-- INSERT: admin or vendedor can create payments
CREATE POLICY "Users can create payments in own accounts"
  ON public.payments FOR INSERT
  WITH CHECK (
    account_id = ANY(get_user_account_ids())
    AND get_user_role_in_account(account_id) IN ('admin', 'vendedor')
  );

-- UPDATE: admin or vendedor can update payments
CREATE POLICY "Users can update payments in own accounts"
  ON public.payments FOR UPDATE
  USING (account_id = ANY(get_user_account_ids()))
  WITH CHECK (get_user_role_in_account(account_id) IN ('admin', 'vendedor'));

-- DELETE: admin only
CREATE POLICY "Admins can delete payments"
  ON public.payments FOR DELETE
  USING (
    account_id = ANY(get_user_account_ids())
    AND get_user_role_in_account(account_id) = 'admin'
  );
```

### Logica de Negocio

- **Pagamento simples:** 1 registro em `payments` com `amount = order.total`
- **Pagamento misto:** N registros em `payments` onde `SUM(amount) = order.total`
- **Boleto:** `is_third_party = true` — no acerto semanal, o valor do boleto nao conta como receita liquida para o Tiago (o dinheiro vai para a Boa Mesa), mas o lucro (markup sobre custo) fica com ele
- **Pre-selecao:** Quando o cliente e selecionado no pedido, `clients.default_payment_method` pre-popula o campo. Tiago pode mudar.

### API Pattern

Usar Supabase client direto (sem API route). Criar payments junto com o pedido:

```typescript
// Dentro do fluxo de criacao de pedido:
const { data: order } = await supabase.rpc('create_order', { ... });

// Criar payments
for (const payment of payments) {
  await supabase.from('payments').insert({
    account_id: activeAccountId,
    order_id: order.id,
    method: payment.method,
    amount: payment.amount,
    is_third_party: payment.method === 'boleto',
  });
}
```
