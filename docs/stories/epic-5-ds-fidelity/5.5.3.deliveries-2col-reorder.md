## Story
**As a** operador do DistriAll,
**I want** montar rotas em 2 colunas (pedidos disponiveis + rota montada) com reordenacao,
**so that** eu organize a sequencia de entregas arrastando ou usando setas.

## Acceptance Criteria
1. Layout 2 colunas: esquerda "Pedidos disponiveis", direita "Rota montada"
2. Mover pedido da esquerda para a rota (clique ou drag)
3. Reordenar itens na rota (drag-and-drop ou setas up/down)
4. Numeracao sequencial (1, 2, 3...) nos itens da rota
5. Botao "Enviar rota" que muda status para "enviada" + toast
6. Empilha em 1 coluna no mobile (<768px)

### ATENCAO: da-grid--cols2 requer import de layout.css

A classe `da-grid--cols2` esta definida em `packages/design-system/tokens/layout.css` mas esse arquivo NAO esta importado em `apps/web/src/app/globals.css`. O executor deve escolher UMA das abordagens:

**Opcao A (preferida — alinha com o DS):** Adicionar ao topo de `globals.css`:
```css
@import "../../../../packages/design-system/tokens/layout.css";
```

**Opcao B (alternativa Tailwind sem novo import):** Usar classes Tailwind equivalentes:
```tsx
<div className="grid grid-cols-2 gap-4 max-md:grid-cols-1">
```

A Opcao A e preferida para manter fidelidade com o DS. A Opcao B e segura se o executor preferir nao adicionar novo CSS global.

## Validation / Testing

**Cenarios manuais a verificar:**

1. **Layout desktop (>=768px):** dois paineis lado a lado. Esquerda: "Pedidos disponiveis". Direita: "Rota montada".

3. **Adicionar pedido:** clicar em pedido disponivel → move para "Rota montada" com numero sequencial (1, 2, 3...).
4. **Reordenar:** arrastar item na rota OU usar setas chevron-up/chevron-down → sequencia atualiza.
5. **Numeracao:** ao reordenar, numeros redistribuidos corretamente (1 sempre o primeiro, etc).
6. **Enviar rota:** clicar "Enviar rota" → toast de confirmacao → status muda para "enviada".
7. **Rota enviada:** botao "Enviar rota" desabilitado/ocultado. Itens nao editaveis.
8. **Painel esquerdo vazio:** EmptyState quando todos os pedidos foram adicionados a rota.
9. **Painel direito vazio:** EmptyState quando nenhum pedido foi adicionado.

### Code Quality Assessment

Implementation is clean and well-structured. The three-file decomposition (page.tsx as state owner, route-builder.tsx as right panel, available-orders.tsx as left panel) follows the established pattern in the codebase. DS token usage is consistent throughout: badge uses `var(--accent-soft)`, `var(--accent-fg)`, `var(--text-xs)`, `var(--weight-bold)`, `var(--radius-full)` exactly matching the canonical DeliveriesScreen.jsx reference.

The `da-grid da-grid--cols2` layout with `layout.css` import (Option A) correctly aligns with the DS. The media query at `max-width: 767px` in layout.css stacks panels to single column on mobile, satisfying AC6.

One minor concern: `account_name` badges in `route-item.tsx:73` and `available-orders.tsx:68` use raw Tailwind `bg-gray-100 px-2 py-0.5 text-xs text-gray-600` instead of DS tokens. This creates a visual inconsistency with the rest of the UI which uses `var(--*)` tokens.

Remove-from-draft flow has a potential silent bug: `handleRemoveItem` in page.tsx:128 filters by `item.delivery_item_id`, but draft route items created via `handleAddOrder` when `!currentDelivery` only have `item.id` (order id), not `delivery_item_id`. The remove button in route-builder.tsx:145 is guarded by `item.delivery_item_id &&` condition — so the button won't show for pure draft items. This means users cannot remove an order from the draft route. This is a functional gap but it is pre-existing architecture, not introduced by this story.
